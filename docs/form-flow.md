# Флоу отправки формы — от полей до ответа внешней системы

Форма редко заканчивается на «Спасибо!». Чаще так: собрали данные → отправили
во внешнюю систему → **посмотрели, что она ответила** → и уже от ответа решили,
что показать человеку.

Это и есть флоу. Настраивается в конструкторе, вкладка **«Флоу отправки»**,
без единой строчки кода.

```
поля  →  кнопка  →  куда уходит JSON  →  правила разбора ответа  →  что показать
 (1)      (2)             (3)                     (4)                    (5)
```

Пункт (5) — это одно из трёх: **показать сообщение**, **показать новые поля**
(следующий шаг) или **перейти по ссылке**.

---

## Канонический пример: заявка на кредит

Готовая форма есть в демо-аккаунте — `credit_application`. Открывается в
конструкторе и работает из коробки против встроенного мока скоринга.

| Шаг | Что происходит |
|---|---|
| **1. Заявка** | ФИО, телефон, дата рождения, сумма, доход → кнопка «Узнать решение» |
| → | JSON уходит REST-запросом в систему принятия решения |
| **Ответ** | `{"decision": "approved", "approvedLimit": 300000, ...}` |
| **Правила** | `approved` → шаг 2 · `declined` → сообщение об отказе · `manual` → сообщение о проверке |
| **2. Оформление** | Одобренная сумма (подставлена из ответа), паспорт, работа, карта → «Оформить кредит» |

Отказ и ручная проверка заканчивают форму сообщением — никакого второго экрана
не появляется. Одобрение открывает шаг 2, **уже заполненный** одобренной суммой
из ответа.

### Ручки для тестов

В сборку встроены два мока системы принятия решения — подключение
«Система принятия решения (mock)» уже настроено на них.

| Ручка | Поведение |
|---|---|
| `POST /decision` | **Детерминированная**: вердикт зависит от суммы и дохода. На ней держатся автотесты |
| `POST /decision-random` | **Случайная**: равновероятно `approved` / `declined` / `manual` — гонять флоу руками |

`/decision-random` принимает параметры прямо в адресе шага:

| Параметр | Смысл |
|---|---|
| `?limit=100` | Сумма одобрения, ₽ (по умолчанию **100**) |
| `?decision=approved` | Зафиксировать исход (`approved` / `declined` / `manual`), когда нужна конкретная ветка, а не грань кубика |

```
Адрес (endpoint):  /decision-random?limit=100
```

Формат ответа тот же, что у `/decision` — поле `decision`, сумма в
`approvedLimit`, — так что правила при переключении между ручками
переписывать не нужно.

```json
{ "requestId": "REQ-482913", "decision": "approved", "approvedLimit": 100, "rate": 17.9 }
{ "requestId": "REQ-118204", "decision": "declined", "reason": "Отказ по результатам скоринга" }
{ "requestId": "REQ-900311", "decision": "manual",   "approvedLimit": 100,
  "reason": "Нужны дополнительные документы",
  "requiredDocs": ["Справка о доходах", "Копия трудовой книжки"] }
```

Ветка `approved` возвращает ещё и `echo` — тело, которое реально дошло до
«внешней системы». Удобно, когда отлаживаете свой JSON-шаблон: видно, что
именно уехало, а не что задумывалось.

## 1. Поля и шаги

Поле принадлежит шагу. У поля в редакторе появляется селектор **«Шаг флоу»**
(как только шагов больше одного); поле без явного шага живёт на первом.

Пока флоу не дошло до шага, его поля:

- не показываются,
- **не проверяются на обязательность** — иначе первый экран было бы не отправить.

Данные накапливаются: второй запрос уносит и то, что ввели на первом экране.
Внешней системе почти всегда нужна и сумма из заявки, и паспорт из добора.

## 2. Кнопка

Текст, текст во время отправки («Проверяем…»), размер, ширина, выравнивание,
красный вариант для необратимых действий. У каждого шага — своя кнопка:
«Узнать решение» на первом, «Оформить кредит» на втором.

## 3. Куда отправлять JSON

| Режим | Когда |
|---|---|
| **Никуда** | Данные только сохраняются в «Заполнениях» |
| **Вебхук (URL)** | Свой URL. В фоне с ретраями (по умолчанию) или с ожиданием ответа |
| **REST через подключение** | Через раздел «Подключения»: базовый URL, авторизация, whitelist, таймаут |

**Разбирать ответ можно только там, где ответ есть.** Фоновая доставка вебхука
отдаёт форме пустой ответ — конструктор предупреждает об этом прямо в блоке.
REST-шаг всегда синхронный: без ответа ветвиться не по чему.

Секреты подключения (токены, ключи) подставляются на бэкенде и в браузер не
попадают — ровно как в справочниках и подсказках.

### Тело запроса

- **Конверт** — `{formId, submissionId, step, data, submittedAt}` (по умолчанию);
- **Только данные** — `{"data": {…}}`;
- **Свой JSON-шаблон** — полный контроль:

```json
{
  "sum": "{{amount}}",
  "client": { "fio": "{{fio}}", "phone": "{{phone}}" }
}
```

Плейсхолдер **целиком в кавычках** подставляется с типом: `"{{amount}}"` уедет
числом `250000`, а не строкой `"250000"`. Внутри строки — как текст с
экранированием, так что кавычка в ФИО не разломает JSON.

## 4. Правила разбора ответа

Правила проверяются **сверху вниз, срабатывает первое подошедшее**. Правило без
условий — это «иначе», его место в конце.

Условие берёт значение из одного из четырёх источников:

| Источник | Что это | Пример пути |
|---|---|---|
| Поле ответа | тело ответа внешней системы | `decision`, `result.offers.0.limit` |
| HTTP-статус | код ответа | — |
| Поле формы | то, что ввёл пользователь | `amount` |
| Ошибка связи | текст сетевой ошибки (пусто, если ответ пришёл) | — |

Операторы: `равно`, `не равно`, `больше/меньше (или равно)`, `одно из`,
`содержит`, `по регулярке`, `заполнено`, `пусто`. Несколько условий соединяются
как «все» или «любое».

Числа сравниваются как числа: `"1 200,50" > 1000` — истина. Нечисловое значение
в числовом сравнении даёт «не подошло», а не падение.

### Ветвление по сумме, а не только по вердикту

«Одобрено, но меньше запрошенного» — отдельный сценарий, и он выражается
условиями по числу:

| Правило | Когда | То |
|---|---|---|
| 1. Одобрено полностью | `decision` равно `approved` **и** `approvedLimit` больше или равно `amount` (поле формы) | Показать шаг «Оформление» |
| 2. Одобрено частично | `decision` равно `approved` | Показать шаг «Согласие на меньшую сумму» |
| 3. Отказ | `decision` равно `declined` | Показать сообщение |

Правило 2 не проверяет сумму повторно: до него доходит только то, что не
подошло правилу 1. В этом смысл порядка «сверху вниз» — частные случаи выше,
общие ниже.

### Тест до публикации

Внизу блока — **«Тест: какое правило сработает»**: вставьте образец ответа и
статус, нажмите «Проверить». Видно, какие правила подошли, какие нет, и что
именно увидит пользователь. Тест гоняет **тот же движок**, что и боевой submit,
и работает по черновику — проверять можно до публикации.

## 5. Что показать

### Сообщение

Тип (успех / инфо / внимание / ошибка), заголовок и текст. В тексте работают
подстановки:

```
{{resp.reason}}              — поле из ответа
{{resp.approvedLimit}}       — вложенные пути через точку
{{phone}}                    — поле формы
{{status}} {{submissionId}}  — служебные
```

Отсутствующее значение становится пустой строкой, а не текстом `{{resp.x}}`.

### Новые поля (следующий шаг)

Выбирается шаг, который откроется. Плюс **подстановки**: поле шага ← путь в
ответе. Так одобренный лимит попадает в поле «Одобренная сумма» до того, как
пользователь увидит экран. Голый путь сохраняет тип (число останется числом),
шаблон со скобками собирает строку.

### Переход по ссылке

URL (с подстановками, например `?id={{submissionId}}`), задержка перед
переходом и «в новой вкладке».

---

## Что уходит в браузер

Правила считаются **на бэкенде**. В страницу приходит только готовый исход:
текст сообщения, id следующего шага и подставляемые значения.

Сырой ответ внешней системы **не попадает в браузер**, пока автор не включит
галочку «Отдавать сырой ответ». Скоринговый балл, причина отказа во внутренней
формулировке, чужие персональные данные — всё это остаётся на сервере по
умолчанию, а не по недосмотру.

## Когда что-то сломалось

Ошибка внешней системы **никогда не превращается в «Спасибо!»**. Если запрос не
дошёл или вернулся не-2xx, а среди правил нет ни одного по `HTTP-статус` или
`Ошибка связи` — форма отвечает 502 и показывает человеку внятную ошибку.

Хотите обработать это сами — добавьте правило:

```
Когда: Ошибка связи · заполнено
То:    Показать сообщение «Решение пока недоступно, мы вернёмся позже»
```

С этого момента ответственность на вас, и молчаливого успеха всё равно не будет:
правило показывает ровно то, что вы написали.

## Многошаговость и безопасность

Второй шаг дописывает данные в **то же самое заполнение**, а не заводит новое.
`submit` — публичный эндпоинт, поэтому продолжение принимается только вместе с
`flowToken` — HMAC-подписью, выданной на предыдущем шаге. Без неё чужой
`submissionId` подобрать и дописать в чужую заявку нельзя.

## События виджета

```js
const form = document.querySelector('no-code-form');
form.addEventListener('form:outcome', (e) => console.log(e.detail.outcome));
form.addEventListener('form:step',    (e) => console.log('перешли на', e.detail.step));
```

`form:submit` и `form:completed` теперь несут ещё и `step`, а `form:completed` —
посчитанный `outcome`.

## API

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/api/forms/:pk/flow` | Нормализованный флоу черновика (то, что исполнится) |
| POST | `/api/forms/:pk/flow/test` | Прогон правил шага по образцу ответа |
| POST | `/api/public/forms/:formId/submit` | Шаг флоу: `{data, step, submissionId, flowToken, context}` |

Ответ submit:

```json
{
  "ok": true,
  "submissionId": "sub_…",
  "flowToken": "…",
  "step": "main",
  "matchedRule": "approved",
  "outcome": { "kind": "fields", "stepId": "approved", "values": { "approved_limit": 300000 } }
}
```

## Совместимость

Формы, настроенные до появления флоу (одиночный `webhookUrl` + «Сообщение об
успехе»), продолжают работать без правок: бэкенд на лету превращает их в один
шаг `main` с безусловным правилом. Настройки не теряются — они видны во вкладке
«Флоу отправки» уже в новом виде.
