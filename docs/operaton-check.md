# Как это работает и как проверить

Две части: сначала объяснение на пальцах, потом три сценария проверки — от
десятиминутного до полного.

---

## Часть 1. Как это работает

### Одним абзацем

Раньше сотрудник открывал задачу и видел форму, которую нарисовал сам Оператон.
Теперь эту форму можно **один раз перенести в конструктор**, причесать — и сотрудник
будет видеть нашу версию. Когда он нажмёт «Отправить», данные уйдут обратно в
процесс, задача закроется, процесс пойдёт дальше. Оператон по-прежнему управляет
процессом; мы взяли на себя только внешний вид формы.

### Две половины, которые важно не путать

Всё делится на два момента времени, и половина вопросов снимается, если держать их
раздельно.

**Момент первый — вы настраиваете форму (один раз).**
Заходите в конструктор, забираете форму из Оператона, правите, публикуете.
Сотрудников это не касается, процессы в этот момент не трогаются.

**Момент второй — сотрудник работает (каждый день).**
Открыл задачу → система смотрит, есть ли для этой формы наша версия → если есть,
показывает её; если нет, показывает старую → сотрудник заполнил и отправил → задача
закрылась.

### Почему нельзя «просто прописать ссылку один раз»

Это единственное неочевидное место во всей истории.

У формы есть **имя** — например `form_obrashchenieKlienta_klassifikaciya`. Оно одно
на все времена, его мы и знаем при импорте.

А у **задачи** есть свой номер, и он новый каждый раз. Клиент прислал обращение —
появилась задача №1. Второй клиент — задача №2. У них одна и та же форма, но
закрывать надо конкретную задачу.

Поэтому адрес возврата хранится с «дыркой»:

```
.../api/tasks/{сюда подставится номер задачи}/complete
```

Номер задачи подставляется в тот момент, когда сотрудник нажимает «Отправить».
Если номер не передали — система честно говорит об ошибке, а не делает вид, что всё
хорошо.

### Что происходит, когда сотрудник жмёт «Отправить»

1. Данные уходят к нам, мы их сохраняем.
2. Мы **сразу же** стучимся в процесс: «закрой задачу №такую-то, вот ответы».
3. Ждём ответ и показываем его человеку:
   - получилось → «Задача отправлена в процесс»;
   - коллега успел раньше → «Задача уже завершена другим пользователем»;
   - процесс недоступен → так и говорим, данные при этом не потеряны.

Специально сделано **синхронно**, то есть с ожиданием. Обычные формы у нас
отправляют данные в фоне с повторными попытками, но здесь так нельзя: человек
должен узнать про «уже закрыто» сразу, а не получить «Спасибо» и потом гадать,
почему процесс не двинулся.

### Почему нельзя переименовывать поля

Поля, приехавшие из Оператона, — это не просто поля, а **имена переменных процесса**.
Процесс по ним принимает решения: «если `klassifikaciya_result` равно
`back_office_required`, идём в бэк-офис».

Переименуете поле — процесс перестанет находить свою переменную. И сломается не
сразу, а в тот момент, когда сотрудник нажмёт «Отправить». Поэтому ID у таких полей
заблокирован. Всё остальное — подпись, тип, порядок, оформление — меняйте свободно.

### Если одна из систем выключена

| Что выключено | Что будет |
|---|---|
| Связь с sota-bpmn | Импорт из файла работает, в модалке видно предупреждение |
| sota-forms целиком | Сотрудник видит старую форму Оператона, как раньше |
| Форма ещё не опубликована | Сотрудник видит старую форму — черновик не перехватывает живую задачу |

Ничего не падает. Каждый выключенный кусок просто возвращает поведение к прежнему.

## Часть 2. Проверка

### Сценарий А — за 10 минут, Оператон не нужен

Проверяет всё, кроме последнего шага (реального закрытия задачи). Хватает, чтобы
убедиться, что импорт, раздел, редактор и сборка адреса возврата работают.

**Запуск**

```bash
cd sota-forms
docker compose up --build
```

Открыть http://localhost:5173, войти `demo@sota.forms` / `demo12345`.

**1. Старые формы не пострадали**

Раздел «Формы». У демо-формы `order_form` в колонке «Источник» — тег **«Своя»**.

> Это проверка миграции: у существующих форм появилась новая колонка в базе, и они
> продолжают работать.

**2. Раздел пока пуст**

Переключатель источника → **«Из Оператона»**. Ожидаем: пусто, надпись «Форм из
Оператона пока нет» и кнопка импорта.

**3. Импорт**

«Импорт из Оператона» → вкладка **«Из файла .form»** → перетащить файл:

```
backend/tests/fixtures/operaton/form_obrashchenieKlienta_klassifikaciya.form
```

Ожидаем:

| Что смотреть | Ожидаемое |
|---|---|
| Сводка | Распознано 2, перенесено полей 2, предупреждений 0, не поддержано 0 |
| Предпросмотр | «Решение» — выпадающий список с 3 вариантами, «Комментарий» — многострочное поле |
| form-id | предзаполнен `form_obrashchenie_klienta_klassifikaciya` |
| Название | **пустое и обязательное**, с подсказкой «в схеме Оператона названия нет» |

> Обратите внимание на form-id: в Оператоне форма называется
> `form_obrashchenieKlienta_klassifikaciya` (с заглавной K), а у нас ключ встраивания
> может быть только строчными. Простое приведение к нижнему регистру дало бы
> нечитаемое `form_obrashchenieklienta_...`, поэтому слова разделяются подчёркиванием.

Впишите название «Классификация обращения» → **Импортировать**.

**4. Редактор**

Откроется редактор формы. Ожидаем в шапке: тег **«Из Оператона»** и рядом серым —
ключ формы.

**5. Защита переменных процесса**

Откройте поле «Решение». Ожидаем: **поле «ID поля» заблокировано**, под ним подпись
про переменную процесса.

Поменяйте «Заголовок» на «Решение по обращению» → Применить → **Сохранить**.
Ожидаем: сохранилось, тег «Из Оператона» на месте (правка не превратила форму в свою).

**6. Публикация**

Кнопка **«Опубликовать»**. Ожидаем: статус «Опубликована v1».

**7. Раздел работает**

Вернуться в «Формы»:

- **«Из Оператона»** → ваша форма, тег фиолетовый, при наведении на тег — ключ формы;
- **«Свои»** → вашей формы нет, `order_form` есть.

**8. Адрес возврата собирается правильно**

Это ключевая проверка. Два запроса в терминале.

Без номера задачи:

```bash
curl -s -X POST http://localhost:8000/api/public/forms/form_obrashchenie_klienta_klassifikaciya/submit \
  -H 'Content-Type: application/json' \
  -d '{"data":{"klassifikaciya_result":"back_office_required"}}'
```

Ожидаем **400** и текст: «Форма ожидает контекст выполнения... встраивайте виджет с
атрибутом task-id». Это правильное поведение, а не поломка.

С номером задачи:

```bash
curl -s -X POST http://localhost:8000/api/public/forms/form_obrashchenie_klienta_klassifikaciya/submit \
  -H 'Content-Type: application/json' \
  -d '{"data":{"klassifikaciya_result":"back_office_required"},"context":{"taskId":"test-1"}}'
```

Ожидаем **502** «Не удалось передать данные в процесс» — потому что sota-bpmn сейчас
не запущен. Это тоже правильный ответ: он доказывает, что адрес собрался и попытка
была.

Теперь откройте в админке **«Доставки (worker)»**. Ожидаем строку, в адресе которой
видно `/api/tasks/test-1/complete` — номер задачи подставился в шаблон.

**9. Резолвер находит опубликованную форму**

```bash
curl -s http://localhost:8000/api/public/forms/by-operaton/form_obrashchenieKlienta_klassifikaciya
```

Ожидаем **200** и в ответе ваш `form_id`. Это тот запрос, которым sota-bpmn узнаёт,
что форму надо рисовать нашим виджетом.

> Хотите проверить, что черновик не перехватывает задачу: заархивируйте форму или
> импортируйте вторую и не публикуйте — на неопубликованную этот запрос вернёт 404.

### Сценарий Б — полная связка с живым процессом

**Порты пересекаются**, это надо развести заранее:

| Сервис | Порт |
|---|---|
| Operaton (движок) | 8080 |
| sota-bpmn backend | 8081 |
| sota-bpmn frontend | 5173 |
| sota-forms backend | 8000 |
| sota-forms frontend | **5180** (иначе конфликт с фронтом sota-bpmn) |

**1. Поднять sota-bpmn с движком**

```bash
cd sota-bpmn
docker compose up -d postgres operaton backend
python -m backend.scripts.seed_processes     # задеплоить процессы из ./seeds

cd frontend && npm install && npm run dev    # http://localhost:5173
```

**2. Прописать связь в обе стороны**

В sota-bpmn (перед стартом backend):

```bash
SOTA_FORMS_URL=http://localhost:8000
FORMS_WEBHOOK_TOKEN=придумайте-длинный-пароль
```

В sota-forms:

```bash
cd sota-forms
SOTA_BPMN_BASE=http://localhost:8081 \
SOTA_BPMN_TOKEN=тот-же-самый-пароль \
WEB_PORT=5180 docker compose up --build
```

> Если sota-forms запущен в Docker, а sota-bpmn — на хосте, `localhost` внутри
> контейнера указывает на сам контейнер. Тогда вместо `localhost` подставьте
> `host.docker.internal` (macOS/Windows) или IP docker-моста, обычно
> `172.17.0.1` (Linux). Самый простой обход — поднять backend sota-forms не в
> контейнере, тогда `localhost` работает у обоих.

**3. Проверить, что системы видят друг друга**

В sota-forms: «Импорт из Оператона». Ожидаем: **нет красного предупреждения**, в
выпадающем списке видны процессы, а после выбора процесса — его формы.

Это и есть проверка того, что связь поднялась.

**4. Импортировать и опубликовать**

Как в сценарии А, но выбирая форму из каталога, а не из файла.

**5. Запустить процесс и открыть задачу**

В sota-bpmn (http://localhost:5173) запустите экземпляр процесса «Обращение клиента»
и откройте появившуюся задачу.

Ожидаем: **видна ваша форма**, а не старая форма Оператона. Отличить легко — у вашей
другое оформление и то название поля, которое вы поменяли на шаге 5 сценария А.

**6. Отправить**

Заполните и отправьте. Ожидаем: «Задача отправлена в процесс», задача пропала из
списка, процесс двинулся дальше.

**7. Убедиться, что данные дошли до движка**

Откройте Cockpit — http://localhost:8080/operaton/app/cockpit — найдите экземпляр
процесса и посмотрите его переменные. Ожидаем: `klassifikaciya_result` со значением,
которое вы выбрали.

> Это финальная проверка: данные не просто «ушли», а легли в процесс под правильным
> именем переменной.

**8. Проверить предзаполнение и защиту от двойной отправки**

- Запустите ещё один экземпляр, откройте задачу, что-то введите, **не отправляйте**,
  закройте и откройте заново. Ожидаем: введённое на месте.
- Откройте одну задачу в двух вкладках, отправьте в первой, потом во второй.
  Ожидаем во второй: **«Задача уже завершена другим пользователем»**.

### Сценарий В — автотесты, одна команда

Самый быстрый способ убедиться, что ничего не разъехалось.

**sota-forms** (нужен PostgreSQL):

```bash
cd sota-forms/backend
pip install -r requirements.txt
TEST_DATABASE_URL=postgresql+asyncpg://forms:forms@localhost:5432/forms_test pytest -q
```

Ожидаем: **121 passed**. Без базы интеграционные тесты честно уйдут в skip, а не
притворятся зелёными; юнит-тесты конвертера (59 штук) пройдут в любом случае:

```bash
pytest tests/test_operaton.py -q      # 59 passed, база не нужна
```

**sota-bpmn**:

```bash
cd sota-bpmn
pytest backend/tests -q               # 110 passed
cd frontend && npm test               # 283 passed
```

## Шпаргалка: что где смотреть, если что-то не так

| Симптом | Куда смотреть |
|---|---|
| В модалке импорта красное предупреждение | Не задан `SOTA_BPMN_BASE` или сервис не поднят |
| «Файл не похож на форму Оператона» | Загружен `.bpmn` вместо `.form` — нужна форма, а не схема процесса |
| Сотрудник видит старую форму | Форма не опубликована, либо не задан `SOTA_FORMS_URL` в sota-bpmn |
| «Нет доступа к процессу: проверьте общий секрет» | `SOTA_BPMN_TOKEN` и `FORMS_WEBHOOK_TOKEN` не совпадают |
| «Форма ожидает контекст выполнения» | Виджет встроен без `task-id` |
| Не даёт сохранить форму, ругается на поля | Вы переименовали или удалили переменную процесса — верните ID |
| Ушли ли данные в процесс | Админка → «Доставки (worker)» |
